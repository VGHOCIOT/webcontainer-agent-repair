# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

A self-healing, backend-less "micro-SaaS builder" demo: an agent writes code for a small app spec, runs it in a real in-browser Node.js sandbox, and iteratively patches it based on actual runtime errors until it works (or hits a retry cap).

## Commands

- `npm run dev` — Vite dev server (the app runs entirely in the browser; needs an Anthropic API key entered in the UI or via `VITE_ANTHROPIC_API_KEY` in `.env`).
- `npm run build` — `tsc -b && vite build` (full typecheck + production bundle).
- `npm run lint` — oxlint (config in `.oxlintrc.json`).
- `npx tsc --noEmit` — typecheck only, without building.

There is **no test runner** in this project — no unit/integration test framework is set up, so there is no single-test command. "Verification" here means running the app and driving the agent loop end-to-end in the browser (see the design constraints below on why the loop's behavior, not a test suite, is the signal). Don't assume a test command exists; if you add one, update this file.

## Architecture (implemented)

- **In-browser runtime** (`src/lib/webcontainer.ts`): WebContainers (`@webcontainer/api`). Boots a real Node.js process with a working filesystem and `npm install` entirely inside the browser tab — no server-side execution. This is the core "no backend" property.
- **Agent loop** (`src/lib/agentLoop.ts`): write → install → start → validate, capped at `MAX_ITERATIONS` (currently 6). Each iteration asks Claude for code (`src/lib/anthropic.ts`), applies it to the container filesystem, and on any failure (no files / install / startup / wrong behavior) feeds the actual captured output back as the next prompt (`buildRetryPrompt` in `src/lib/spec.ts`). Returns `{ attempts, stoppedReason }`.
  - **Diff-apply, not blind re-mount** (`applyGeneratedFiles` in `webcontainer.ts`): after the first attempt, only the file *delta* is written and files the model dropped are removed (`mount` merges and never deletes, so a stale module would linger and mask the bug).
  - **No-progress guard**: tracks a file fingerprint and a failure signature per attempt; a repeat escalates the retry prompt (`buildEscalatedRetryPrompt`) and two consecutive stalls stop the loop with `stoppedReason: "no-progress"`, so a stuck run can't burn the whole budget.
- **Interaction-level grading — the frontend grader** (`src/lib/previewDriver.ts`): the loopback validator (below) only sees served HTML/JSON over localhost, so it can only grade the *data layer*. This grades the *frontend*: `setPreviewScript` injects a per-spec driver into the preview; after the loopback validator passes, the loop loads the app in a hidden, driver-flagged iframe where the driver performs real DOM interactions (type/click/toggle) and asserts on the result, then `postMessage`s the same `{ checks: [...] }` contract back — merged into validation like fuzz. A real browser driving the real UI, no backend, no Selenium. This is the keystone that lets a genuine *frontend* bug be detected, fed back, and healed on screen. Drivers are model-authored per-spec (`src/lib/driverGen.ts`, a `validatorGen` sibling — the strong `validatorModel` writes a deterministic `runChecks()` body once, run unchanged every attempt), surfaced and regenerable in an "Interaction driver" panel like the validator. `TASKS_SPEC` in `interactive.ts` is the canonical interactive spec. The injected script stays passive in the visible preview (runs interactions only when the `__agentDrive=1` flag is present) so it never mutates the UI the user is watching.
- **Validation is generated per-spec — "Mode A"** (`src/lib/validatorGen.ts`, `src/lib/validate.ts`): one AI call turns the freeform spec into a deterministic Node validator *script*; the loop then runs that fixed script every attempt, so the grader is deterministic at run time and only its authoring uses the model. This deliberately replaced an earlier hardcoded validator and an earlier "keep validation non-AI" stance. **Mode B (an LLM judging each attempt) was rejected** — a non-deterministic grader in the fitness-function seat corrupts convergence data and is gameable by the code generator. Every validator honors a shared per-check contract: it prints `{ checks: [{ name, pass, details }] }` as its last stdout line.
- **Frontend shell** (`src/App.tsx`, `src/components/`): React/TS. Shows a validator panel (generated script + check chips + Regenerate), a live attempt log, the live preview pane, run stats, a **healing timeline** (`computeHealingTimeline` in `src/lib/stats.ts` + `HealingTimeline.tsx`) — a check×attempt grid that flags pass→fail regressions — and a **preview replay** (`PreviewReplay.tsx`) that steps through the rendered DOM each attempt produced (captured by the interaction driver, stored as `attempt.previewSnapshot`, replayed in a scripts-disabled `srcdoc` iframe) so the visual break→heal is watchable and exportable to a self-contained file. The healing process must stay visible, not just the end result. All of this is in-session/ephemeral — the only way data leaves is a user-initiated Export download, never a persisted store (keeps the no-backend/no-DB thesis intact).

## Styling conventions (keep consistent across additions)

- **Design tokens only — no hardcoded hex in components.** All color/radius comes from the tokens in `src/index.css`: neutrals (`--bg`, `--fg`, `--muted`, `--surface`, `--surface-raised`, `--code-bg`, `--code-fg`, `--border`, `--border-strong`), brand (`--accent*`), semantics (`--pass`/`--fail`/`--warn`/`--info` each with a `-soft` background), and radii (`--radius-sm|--radius|--radius-lg|--radius-pill`). Both light and dark must look correct — the toggle (`ThemeToggle`, sets `data-theme` on `<html>`) exists to check. The two `#fff` preview/replay frame backgrounds are deliberate (rendered app pages assume white) and the thumb-label green/red literals sit on an opaque dark chip; everything else is a token.
- **Controls are standardized:** buttons are primary (accent fill, action bar) / secondary (`.button--secondary`, accent outline) / the `.theme-toggle` ghost; size comes from context, variant only sets color. Status **pills** use `--radius-pill`, rectangular **chips** use `--radius-sm`. Reuse these, don't invent per-component button/pill styling.
- The two graders (validator + interaction driver) are presented as one **Graders** group (`.graders` / `.panel*`), both authored by the single "Grader model" picker — keep them a matched pair, not separate entities.

## Design constraints to preserve

- **Thesis:** the standout claim is an in-browser Node runtime + an autonomous self-healing agent loop that builds, breaks, notices, and fixes a working app entirely in the tab — demonstrating the sandbox as a legitimate space for *frontend* development decoupled from database/backend definitions. So push difficulty into the **frontend dimension** (real UI, client state, interactions — graded by the interaction driver) and keep the data layer a deliberately dumb stub. Do NOT drift toward backend/DB complexity (stateful CRUD, concurrency correctness); that's the axis the project exists to show is *separable*.
- Keep each individual demo app small and legible, but not necessarily trivial: the loop is the point, and the app must be small enough that bugs are predictable yet real enough (and now interactive enough) to read as a legitimate app.
- Bugs shown healing must be genuine, not faked: either let them arise naturally from an underspecified spec, or deliberately seed a known bug class — but if seeded, disclose that transparently rather than presenting it as organic. Two levers now generate genuine, disclosed bugs: (1) a **capability gap** — the builder and validator-author models are decoupled (`builderModel`/`validatorModel` in `App.tsx`), builder defaulting to a weaker model than the strong grader; and (2) **environment perturbations** — e.g. the opt-in PORT-honoring probe (`envPort` in `agentLoop.ts`) launches the app with a non-default `PORT` and fails the startup stage if it comes up elsewhere; the offline-install and fuzz probes; and the opt-in **client-error probe** (`clientErrors`, `src/lib/previewErrors.ts`) which fails an attempt when the live preview iframe throws an uncaught exception / unhandled rejection in the browser — a "server healthy, client throwing" bug the loopback validator can't see. It's timing-dependent on a rendered preview, so it's a Build-path signal, off in batch. The default `DEFAULT_SPEC` is deliberately kept loose (no bug-coaching); grader strictness lives in `VALIDATOR_SYSTEM_PROMPT`, so don't re-add hints to the spec.
- The valuable output is the data on how the loop behaves, not just a working demo: iterations to convergence, which failure classes it handles vs. regresses on, and token/time cost per fix. This is already instrumented (per-attempt `usage`, `failureStage`, per-check results, regression detection) — keep new work capturable this way, not just pass/fail.
- Retry prompts must carry enough context (spec, prior code, actual captured error) for a targeted fix, not a blind full-file rewrite.
- **Every check is either a grader or a perturbation — classify new ones and route them the standard way; do not hand-wire another bespoke stage.** This taxonomy MUST hold for all subsequent check-like additions:
  - **Graders** define *correctness* and run automatically (no user toggle): the loopback validator (always) and the model-authored interaction driver (whenever the spec is a frontend spec — `frontend` flag on the preset, `gradeUI` in `App.tsx`). Graders are surfaced + regenerable in their own panel.
  - **Perturbations** are opt-in, disclosed stressors, off by default so the base run is unperturbed: PORT, offline, fuzz, client-errors. They are checkboxes.
  - **Layer (second axis):** independent of grader/perturbation, every check also belongs to a layer — `data` (server responses over loopback: the validator, fuzz) or `frontend` (behavior that only exists once the browser runs the page: the interaction driver, client errors). Install/startup failures aren't checks; `FailureStage` already classifies them. Each `CheckProbe` declares `kind` and `layer`, and the loop stamps `layer` onto every check it returns (`CheckResult.layer`) so results can be grouped by layer without parsing check names. Report bug classes by layer, not by which probe found them.
  - **Uncaught client errors are also captured by the interaction driver itself:** the harness in `previewDriver.ts` listens for `error` / `unhandledrejection` inside its own hidden iframe and appends a `frontend: no uncaught client errors` check to every driver result. Unlike the standalone `client-errors` probe (live-preview timing, Build path only), this runs in batch. The driver-side capture was confirmed in a live run (a seeded throw-on-load page failed the check with the thrown message), so the standalone probe is now a candidate for retirement.
  - **Composition:** any post-startup, check-*producing* addition (grader or perturbation) is added as a `CheckProbe` pushed onto `checkProbes` in `agentLoop.ts` — an `{ id, run(ctx) → CheckResult[] }` honoring the shared `{ name, pass, details }` contract. The loop runs the list after the loopback validator passes and short-circuits on the first failure. Do NOT add another bespoke `if (x && validation.pass) { … aggregateChecks … }` block. The only checks that live *outside* this pipeline are **stage modifiers** that change install/startup themselves (PORT, offline) rather than producing post-validation checks.
- **Never re-run or rebuild an *unchanged* build per attempt.** A WebContainer build is deterministic: the same bytes, installed and started the same way, reproduce the same install log, startup, and validator verdict every time — so re-executing unchanged code heals nothing, it only burns time/tokens and pollutes convergence data with duplicate rows. The loop advances *only* when the model emits different code. This is why the loop applies the file delta (`applyGeneratedFiles`) rather than rebuilding, and why byte-identical output is treated as a stall by the no-progress guard rather than something to run again. Do not add a "retry the same build" path — there is nothing on the other side of it. (A prior version had exactly this recursive rebuild-per-attempt logic; it added nothing and was removed. Don't reintroduce it.)
